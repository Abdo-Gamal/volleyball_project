<--------------------------- Branches & Merging --------------------------------->

# Create and switch to new branch
git checkout -b branchName 

# Rename branch (while standing on it)
git branch -m new_branch_name                  

# Merge new branch with main
git checkout main          # 1. Go to main branch first
git merge branchName       # 2. Merge the branch into main

# Delete branches
git branch -d <branch_name>             # Delete finished local branch
git branch -D <branch_name>             # Delete unfinished local branch (force)
git push origin --delete <branch_name>  # Delete branch from remote

# Main Rule:
# 1- Do not write code in the main branch. Always use a feature branch.

<--------------------------- Undoing & Resetting -------------------------------->

# Case 1: Wrote wrong code, but did NOT commit yet
git restore .                      # Go back to last commit and remove wrong code
git restore --staged fileName      # Return file from stage area to working area
git clean -n                       # Delete all untracked files (dry run to see what will be deleted)

# Case 2: Reverse a commit (creates a new commit to undo changes safely)
git revert <commit_hash>           # Use it so others can pull this without damaging their work

# Case 3: Delete wrong commit completely (Dangerous)
git reset --hard <commit_hash>     # Deletes commit by changing HEAD pointer to an old commit

<--------------------------- Tags & Releases ------------------------------------>

<--- 1. The Concept (Why do we use them?) --->
Tags and Releases act as a "Save Point" for a stable version of your project 
(e.g., when a specific Baseline is fully working). It allows anyone to download 
that exact working snapshot without getting confused by new daily updates.

- Tag: A core Git feature. It is simply a permanent bookmark pointing to a specific commit.
- Release: A GitHub feature. It wraps around your Tag to add a nice title, description, 
  and automatically generates downloadable zip files for the code.

<--- 2. How to create them? --->

Step 1: On your Laptop (Terminal)
- Create a tag on your current commit:  git tag v1.0
- Push the tag to GitHub:               git push origin v1.0

Step 2: On GitHub (Browser)
1. Go to your repository and click "Releases" on the right side.
2. Click "Draft a new release".
3. Choose the tag you just pushed (v1.0).
4. Write a Release Title and Describe the changes (Release notes).
5. Click "Publish release".

<--- 3. Can I make a Release without a Tag? --->
No. Every Release MUST be attached to a Tag. However, if you forget to create the 
tag locally in the terminal, you can just type a new tag name directly in the 
GitHub Release page, and GitHub will automatically create the Tag for you.

<--- 4. Where do the zip files come from? --->
GitHub automatically generates the "Source code (zip)" and "(tar.gz)" files 
based on the exact code present at the moment the Tag was created.

<--------------------------- Concepts & Use Cases ------------------------------->

<--- Pull Request (PR) --->
Case 1: Working with a team on the same project
When you need it: If you are working in a company or on a group project, and everyone is sharing the same repository.
What happens: Instead of editing the main code directly, you create a separate "Branch". Once finished, you Push it and open a Pull Request. It tells your team: "Please review my code before we merge it."

Case 2: Contributing to someone else's project (Open Source)
When you need it: If you find a GitHub project and want to fix a bug, but lack permission to edit their code directly.
What happens: You take a copy (Fork). You make changes, Push it, and open a Pull Request to the original owner: "I fixed this issue in my version. Please pull it to your original project."

<--- The Full Workflow Case --->
1. Push: Upload your finished branch to GitHub (git push origin featureX).
2. PR: Open GitHub and click "Compare & Pull Request".
3. Merge: Click "Merge" on GitHub to add code to the online main branch.
4. Local is Old: Your laptop's main branch is now outdated.
5. Pull: Run (git checkout main) then (git pull origin main) to download updated code.

<--- Standard Daily Steps --->
1. Update Local Main: git checkout main -> git pull origin main
2. Create a Branch: git checkout -b <branch_name>
3. Save Work Locally: git add . -> git commit -m "message"
4. Push to GitHub: git push origin <branch_name>
5. Open Pull Request on GitHub.
6. Merge PR on GitHub.
7. Sync Laptop: git checkout main -> git pull origin main
8. Clean up: git branch -d <branch_name>

<--- Best Practices for Branching & Merging --->
Branch Naming: Always use clear prefixes like feature/ (additions), fix/ (bug resolutions), docs/ (documentation), and experiment/ (trying new ideas).
Merge Pointers: A branch in Git is just a pointer to your latest commit. When you merge into main, the main pointer moves forward. The old branch pointer is deleted to keep workspace clean.
Branching Latest main: Always create a new branch from the latest main to prevent merge conflicts. Only go back to old commits in emergencies.

<--- What Happens if You Forget to Delete the Remote Branch? --->
Will it come back? No. Running git pull will not bring the deleted branch back.
Why? git pull only updates the current branch. It does not recreate deleted local branches.
How to clean up? git push origin --delete <branch_name>

<--- Understanding git pull origin <branch_name> --->
The Misconception: main in this command refers to your local branch. It does not!
The Breakdown: 
- origin: Refers to the remote server.
- main: Refers to the source branch on the server.
- Destination: The updates are ALWAYS merged into your current active local branch.
The Golden Rule: To update your local main safely, switch to it first (git checkout main), then run git pull origin main.

<--- The Difference: git pull vs. git pull origin main --->
Case 1: git pull (No arguments)
Git checks which branch you are on, goes to the server, downloads updates ONLY for that specific branch, and merges them. It ignores main completely.

Case 2: git pull origin main 
You give a strict command: "Get latest code from main on the server, and merge it into the branch I am standing on right now."

<--- The Difference: Git Reset vs. Git Stash --->
git reset (Unstaging): Removes files from Staging Area, but keeps code on screen. Use to undo an accidental git add.
git stash (Hiding): Takes all uncommitted changes and hides them in a safe box, returning files to a clean state. Use when in the middle of messy work and you urgently need to switch branches. Bring work back later using git stash pop.

<--------------------------- Advanced Daily Tools ------------------------------->

<--- 1. Viewing Exact Changes (git diff) --->
# Before you commit, you might want to double-check exactly which lines of code changed.
git diff                 # See exact additions (green) and deletions (red) in your working area.
git diff --staged        # See the changes ONLY for files you already used 'git add' on.

<--- 2. Fixing the Last Commit (Amend) --->
# If you just made a commit but realized you forgot to include a file (like a config file 
# or a Slurm batch script), or if you just want to fix a typo in the commit message:
git add forgotten_file.py
git commit --amend -m "New updated commit message"
# IMPORTANT: Only use --amend if you haven't pushed the commit to GitHub yet!

<--- 3. Handling Merge Conflicts (حل التعارض) --->
# What happens if Git says "Merge conflict"? 
# This happens when two branches changed the exact same line in a file. Git pauses the merge.
# 
# Step 1: Open the conflicted file in your editor (like VSCode).
# Step 2: You will see Git added markers like this:
<<<<<<< HEAD
(Your current code in the branch you are standing on)
=======
(The incoming code from the branch you are trying to merge)
>>>>>>> feature-branch

# Step 3: Delete the markers (<<<<, ====, >>>>) and edit the code so it looks correct.
# Step 4: Save the file, then tell Git the conflict is resolved by committing:
git add conflicted_file.py
git commit -m "Resolved merge conflict in the architecture file"
