<--------------------------- Setup: Init, Config, Remote ------------------------->
<-------------------------------------------------------------------------------->

# Initialize Git and start tracking changes
git init
# USE CASE: first time starting a new project, you want Git to start tracking it.
# ALTERNATIVE: no real alternative — you either "init" a new repo or "clone" an existing one.

# Delete Git tracking completely (start from scratch)
rm -rf .git
git init
# USE CASE: you want to wipe all old commit history and start clean (repo got messy,
# or has sensitive data you want gone from history).
# ALTERNATIVE: git checkout --orphan new_main  -> makes a new branch with no history,
# without deleting the whole .git folder.

# Example: Full Clean Setup for an ML project
rm -rf .git
git init
echo -e "*.pth\n*.pkl\nvideos/\noutputs/\ndatasets/\n__pycache__/\n.ipynb_checkpoints/\n" > .gitignore
git add .
git commit -m "Initial commit with clean setup"
git branch -M main                         # rename current branch to "main"
# USE CASE: setting up the very first commit of an ML project so heavy files
# (checkpoints, datasets) never get tracked from day one.
# ALTERNATIVE: git init --initial-branch=main  -> names the branch "main" right away,
# no need for "branch -M" after.

# Link local repo to an online (GitHub) repo
git remote add origin https://github.com/username/project.git
git remote -v                              # show the full remote URL(s) (fetch + push)
# USE CASE: connecting your local repo to a GitHub repo for the first time.
# ALTERNATIVE: git remote set-url origin <url>  -> change an existing remote instead
#              of adding a new one.
#              git remote remove origin        -> unlink it.
#              git clone <url>                 -> if starting from a repo that already
#              exists on GitHub (does init + remote add + first pull in one command).

# Set your identity (once per machine, or per repo without --global)
git config --global user.name "YourName"
git config --global user.email "you@example.com"
git config --global --unset user.name      # remove a config value
git config -l                              # show all current configs
git config --global --edit                 # edit config file directly (with color coding)
# USE CASE: first time using Git on a machine, or you need a different email for
# work vs personal projects (drop --global to set it per-repo only).
# ALTERNATIVE: you can edit ~/.gitconfig manually in any text editor instead of --edit.

# SSH key setup (needed to push/pull without typing a password every time)
ssh-keygen -t rsa -b 4096 -C "you@example.com"
# then add the generated public key (~/.ssh/id_rsa.pub) to GitHub > Settings > SSH keys
# USE CASE: so you can push/pull from GitHub without typing a username/password or
# token every single time.
# ALTERNATIVE (newer, preferred): ssh-keygen -t ed25519 -C "you@example.com"
#              -> newer, faster algorithm than RSA.
#              Also: GitHub CLI ("gh auth login") or HTTPS + Personal Access Token
#              instead of SSH entirely.

# Aliases (shortcuts for commands you type a lot)
git config --global alias.st status        # now "git st" = "git status"
git config --global alias.br branch        # now "git br" = "git branch"
git config --global alias.co checkout
git config --global alias.last "log -1 HEAD"
# USE CASE: you type the same long commands often and want to shorten them.
# ALTERNATIVE common aliases to add: alias.unstage "reset HEAD --"
#              alias.lg "log --oneline --graph --all"

<--------------------------- Basic Workflow -------------------------------------->
<-------------------------------------------------------------------------------->

git status                                 # See what changed / staged / untracked
# USE CASE: before doing anything — check what changed, what's staged, what's untracked.
# ALTERNATIVE: git status -s  -> short format, one line per file.

git diff                                   # See exact changes (before staging) - green=added, red=removed
git diff --staged                          # See changes ONLY for files already "git add"-ed
# USE CASE: "git diff" shows changes NOT staged yet. "git diff --staged" shows what
# WILL go into the next commit.
# ALTERNATIVE: git difftool  -> view the diff in a GUI app instead of the terminal.

git add .                                  # Stage all changes
git add a.txt                              # Stage one specific file
git add -p                                 # Stage changes interactively, chunk by chunk
                                            # (useful when one file has 2 unrelated edits
                                            # and you want them in separate commits)
# USE CASE: "add -p" specifically — a file has two unrelated edits and you want them
# split into separate commits (one commit = one logical change).
# ALTERNATIVE: git add -i  -> interactive mode, broader menu of options than -p.

git commit -m "feat: add attention module" # Save a logical checkpoint locally
# USE CASE: after staging changes and you want to save them as a local checkpoint.
# ALTERNATIVE: git commit -am "message"  -> stages already-TRACKED files and commits
# in one step (won't pick up new untracked files).

# File status letters (shown in VSCode / terminal):
#   U = Untracked (new file, Git doesn't know it yet)
#   A = Added / staged (ready to be committed)
#   M = Modified (tracked file, changed since last commit)

<--------------------------- Branch vs Commit ------------------------------------>
<-------------------------------------------------------------------------------->

# Branch = the big independent task
# Commit = one logical step inside that task

feature/attention-model                    # <- Branch (the task)
    commit: feat: add attention module     # <- step 1
    commit: feat: integrate attention      # <- step 2
    commit: fix: correct attention mask    # <- step 3

# A branch can hold 1 commit or 50 commits. Size doesn't matter,
# independence of the task is what matters.
# ALTERNATIVE workflow (whole concept): some teams use "Trunk-Based Development"
# instead of feature branches — tiny commits go straight to main behind feature
# flags. More common in large teams doing continuous deploy.

<-------------------------------------------------------------------------------->

# Format:  <type>/<short-description>   (lowercase, use - not spaces)

feature/person-action-classifier
feature/temporal-transformer

# BAD names (avoid): branch1, test, new, final, mybranch, temp
# USE CASE: every time you start new work — the name tells you what kind of work
# it is without opening the code.
# ALTERNATIVE naming styles:
#   username/feature-name       -> shows who owns the branch (useful in big teams)
#   JIRA-123-short-description  -> common in companies that link branches to tickets

# List all branches:
git branch                                 # local branches
git branch -a                              # local + remote branches
git branch -vv                             # local branches + which remote branch they track
# USE CASE: -a to see remote branches too, -vv to see which remote branch each
# local branch is tracking.
# ALTERNATIVE: git branch --show-current  -> prints just the current branch name
# (handy inside scripts).


<-------------------------------------------------------------------------------->
<--------------------------- Commit Naming --------------------------------------->
<-------------------------------------------------------------------------------->

# Format:  <type>: <short description>

feat: add attention module                 # new feature
fix: correct label mapping                 # bug fix
refactor: simplify dataset loader          # code reorg, no behavior change
docs: update training instructions         # documentation
test: add dataset validation test          # tests
chore: update dependencies                 # maintenance/config
perf: speed up dataloader with num_workers # performance improvement
style: format code with black              # formatting only, no logic change

# RULE: one commit = one logical change (not one file).
# Normal for 3 different commits to all touch model.py.
# Normal for 1 commit to touch model.py + config.py + README.md
# as long as they're part of the SAME logical change.

# BAD:
git commit -m "update"                     # useless, tells you nothing later
git commit -m "final final2"               # avoid this pattern completely
# USE CASE: always — lets you understand every past commit months later without
# opening it.
# ALTERNATIVE: this format is actually a standard called "Conventional Commits"
# (conventionalcommits.org). To enforce it automatically, tools like "Commitizen"
# or "commitlint" block any commit that doesn't follow the format.

# See a commit's details later:
git show <hash>                            # full details of one commit
git log -p -1                              # diff of the LAST commit
git log --author="YourName"                # filter commits by author
# USE CASE: reviewing what a specific commit did, after some time has passed.
# ALTERNATIVE: git log --grep="focal loss"  -> search inside commit messages
# instead of filtering by author.


<-------------------------------------------------------------------------------->
<--------------------------- Branches & Merging ---------------------------------->
<-------------------------------------------------------------------------------->

# Create + switch to a new branch (two equivalent ways, pick one):
git checkout -b branchName                 # older command, still works everywhere
git switch -c branchName                   # newer, clearer command (recommended)
# USE CASE: start of any task (feature/experiment/fix).
# DIFFERENCE: "switch" is newer and clearer (only handles branches), "checkout" is
# older and does many things (branches + restoring files), which can cause confusion.
# Prefer "switch" for branches and "restore" for files.

# Rename the branch you're currently standing on:
git branch -m new_branch_name
# USE CASE: you named the branch wrong and you're currently on it.
# ALTERNATIVE: git branch -m old_name new_name  -> rename a branch you're NOT on.

# Merge a finished branch into main:
git checkout main                          # (or: git switch main)  1. go to main first
git merge branchName                       # 2. merge the branch into main
# USE CASE: merging a finished branch into main locally (no GitHub).
# ALTERNATIVE: "git rebase" instead of "merge" — puts your commits on top of the
# latest main with NO merge commit (linear history). But it rewrites history, so
# never use it on branches shared with other people.

# Delete branches:
git branch -d branch_name                  # delete a FINISHED local branch (safe)
git branch -D branch_name                  # force-delete an UNFINISHED local branch
git push origin --delete branch_name       # delete the branch from GitHub (remote)
# USE CASE: after a branch is merged and you don't need it anymore. Only use -D if
# you're sure you don't need those commits anymore (not merged elsewhere).
# ALTERNATIVE (shorter, remote delete): git push origin -d branch_name

# MAIN RULE: Never write code directly on main. Always use a feature branch.

# A branch is just a movable pointer to a commit. When you merge into main,
# the main pointer moves forward to include the new commits. The old branch
# pointer itself is what gets deleted when you run "branch -d" - the commits
# stay in history (unless it was a squash merge, see below).


<-------------------------------------------------------------------------------->
<--------------------- CASE: When to make a new Branch --------------------------->
<-------------------------------------------------------------------------------->

# CASE 1 - New feature/model
git switch main
git pull
git switch -c feature/attention-model

# CASE 2 - Bug found INSIDE the feature you're already working on
# Don't create a new branch, just commit on the same branch:
git commit -m "fix: correct attention mask"

# CASE 3 - Independent experiment (separate idea, not part of current work)
git switch main
git switch -c experiment/focal-loss

# CASE 4 - Large architecture change (still ONE independent task)
git switch -c feature/temporal-transformer

# CASE 5 - Tiny fix (e.g. one line in README)
# Solo project -> fine directly on main.
# Practicing professional habits -> use docs/fix-readme-command

# CASE 6 - Urgent fix needed on main while mid-feature with uncommitted work
git stash                                  # temporarily hide your uncommitted work
git switch main
git switch -c fix/critical-bug
# ... fix it, commit, push, merge via PR ...
git switch feature/attention-model
git stash pop                              # bring your hidden work back
# USE CASE (case 6): you're mid-way through code, not ready to commit, and suddenly
# need to fix something urgent on main.
# ALTERNATIVE: instead of stash, make a temporary commit like "wip: pause for
# hotfix" on the same branch, come back to it later (then clean it up with
# "commit --amend" or "rebase -i"). Simpler with many pending files, but leaves a
# "messy" commit in history until cleaned.

# ALWAYS branch from the latest main to avoid unnecessary conflicts:
git switch main
git pull
git switch -c feature/new-thing            # only go back to OLD commits in emergencies

# ALTERNATIVE for the whole branching strategy: "Git Flow" (git flow init) forces a
# ready-made branch system (develop, feature/*, release/*, hotfix/*) instead of
# deciding manually like above. Useful for projects with formal releases, overkill
# for a personal ML project.

<--------------------------- Remote: Push / Pull / Fetch ------------------------->
<-------------------------------------------------------------------------------->

git push                                   # Upload LOCAL commits to GitHub (current branch)
                                            # Does NOT mean the branch is finished.
                                            # You can push many times while working.

git push -u origin main                    # first push: -u links local branch to remote branch
git push origin featureX                   # push one specific branch
git push --all origin                      # push ALL local branches at once
# USE CASE: uploading your local commits to GitHub. Use -u only the first time so it
# links the local branch to the remote one automatically (after that, plain
# "git push" is enough).
# ALTERNATIVE: git push --set-upstream origin main  -> same meaning as -u, full name.

# CAUTION about --force:
git push -u origin main --force            # ONLY needed if the remote already has unrelated
                                            # history you must overwrite (e.g. fixing a broken
                                            # first push). Do NOT make --force a habit, and
                                            # NEVER force-push to a shared main others use.
git push --force-with-lease                # safer alternative: refuses if someone else pushed
                                            # new commits you don't have yet
# USE CASE: only in the rare case you must overwrite remote history (e.g. a broken
# first push). Don't make this a habit, never on a shared main.
# BEST PRACTICE: always prefer --force-with-lease over plain --force — it refuses
# if someone else already pushed, protecting you from wiping a teammate's work.

git fetch origin                           # Download info from GitHub, does NOT touch your files
git fetch --prune                          # also remove local refs to branches deleted on GitHub
# USE CASE: you want to see what's new on GitHub WITHOUT merging it into your work yet.
# ALTERNATIVE: git remote update  -> fetches ALL remotes, not just one.

git pull                                   # = git fetch + merge into your CURRENT branch
git pull origin main                       # explicit: fetch "main" from "origin" and merge
                                            # it into whichever branch you're CURRENTLY on
# USE CASE: update the branch you're currently on with the latest from the remote.
# (See the "Understanding git pull" section below — this is the most confusing command.)
# ALTERNATIVE (avoids extra merge commits): git pull --rebase  -> puts your local
# changes on top of the latest update instead of making a merge commit every time.

# note: git pull = git fetch + git merge (always, in both forms above)


<-------------------------------------------------------------------------------->
<------------------- Understanding git pull (common confusion) ------------------>
<-------------------------------------------------------------------------------->

# MISCONCEPTION: "git pull origin main" updates MY LOCAL main branch.
# TRUE MEANING:
#   origin -> the remote server
#   main   -> the SOURCE branch on that server
#   destination -> ALWAYS your current active local branch (whatever you're standing on)
#
# So if you're standing on feature/attention-model and run:
git pull origin main
#   -> it pulls main's updates INTO feature/attention-model, NOT into your local main.
#
# GOLDEN RULE to safely update local main:
git checkout main                          # switch to main FIRST
git pull origin main                       # now it updates the right branch
# USE CASE: this is THE way to correctly update your local main — always switch to
# main first before pulling.
# ALTERNATIVE (one command instead of two): git pull origin main:main  -> explicitly
# tells Git to update main even if you're not on it. Less used because it's less
# obvious — the two-step version above is clearer.

# CASE - git pull (no arguments) vs git pull origin main:
#   git pull              -> uses whatever branch you're on + its configured upstream,
#                             downloads updates ONLY for that branch, merges them.
#   git pull origin main  -> explicit command: "get main from origin, merge into
#                             whatever branch I'm standing on right now."

# CASE - I forgot to delete the remote branch after merging. Will "git pull" bring
# a DELETED branch back?
#   No. git pull only updates your CURRENT branch, it does not recreate deleted
#   branches. To clean it up manually:
git push origin --delete branch_name
# USE CASE: you forgot to delete a remote branch after merging — "git pull" will
# NOT bring it back or delete it for you, you must delete it manually like this.

<------------------------- Merge: Where exactly? --------------------------------->
<-------------------------------------------------------------------------------->

# Professional workflow = Merge happens on GitHub (remote), via Pull Request.

git push -u origin feature/attention-model # 
1) push branch to GitHub (remote)
# 2) On GitHub: Open Pull Request  (feature/attention-model -> main)
# 3) On GitHub: Review / tests
# 4) On GitHub: Click "Merge pull request"   <-- MERGE HAPPENS HERE (remote)
# 5) On GitHub: Delete branch button (deletes remote branch)

# Then locally, sync up:
git switch main
git pull                                   # pulls the merged result into LOCAL main
git branch -d feature/attention-model      # delete the LOCAL branch too
# USE CASE: this is the standard professional workflow — merge on GitHub via Pull
# Request so the code gets reviewed before merging.

# ALTERNATIVE (merge locally instead of a GitHub PR):
git switch main
git merge feature/attention-model          # merge happens LOCALLY
git push                                   # then upload the merged main to GitHub
# USE CASE: fine for a solo project with no team reviewing the code.

# CASE - Merge conflict (locally or after pulling a PR locally):
git merge feature/attention-model
# Git says: CONFLICT (content): Merge conflict in model.py
git status                                 # shows which files have conflicts
# Open the file, you'll see markers like:
#   <<<<<<< HEAD
#   your current branch's code
#   =======
#   incoming branch's code
#   >>>>>>> feature-branch
# Delete the markers, manually edit the code so it's correct, then:
git add model.py
git commit -m "Resolved merge conflict in the architecture file"
# or cancel the whole merge attempt:
git merge --abort
# USE CASE: Git can't automatically combine two files because the same lines
# changed in both branches.
# ALTERNATIVE ways to resolve conflicts: "git mergetool" (GUI tool), or VS Code's
# built-in merge editor (shows Accept Current / Accept Incoming buttons instead of
# hunting for <<<<<<< markers by hand).


<-------------------------------------------------------------------------------->
<---------------------- What shows up after Merge? ------------------------------->
<-------------------------------------------------------------------------------->

# Before merge:
#   main:  A---B
#                \
#                 C---D---E   (feature/attention-model)

# NORMAL merge (default on GitHub):
#   main:  A---B-------M
#                \     /
#                 C---D---E
#   -> All commits C, D, E remain visible + one extra merge commit M.

# SQUASH merge (a GitHub option):
#   main:  A---B---F
#   -> F is ONE new commit combining C+D+E. Individual commits disappear from
#      main's history (still exist on the old branch ref until it's deleted).

# REBASE merge (a GitHub option):
#   main:  A---B---C'---D'---E'
#   -> replayed on top of main, straight-line history, no merge commit.

# CASE - clean up messy commits BEFORE opening the Pull Request:
# You have: "wip" "fix typo" "actual fix" "oops again"
git rebase -i HEAD~4                       # interactive rebase: pick/squash/reword/drop
# result: turns 4 messy commits into 1 clean commit like "fix: correct attention mask"
# (only do this BEFORE pushing, or before anyone else pulled the branch)
# USE CASE: you have messy commits ("wip", "fix typo") before opening a PR and want
# to combine them into one clean commit.
# ALTERNATIVE (simpler, same goal): GitHub's "Squash and merge" button when opening
# the PR — does the same squashing without touching your local history at all
# (easier than doing "rebase -i" by hand).

# USE CASE: you want to look at old code without changing any branch (e.g. compare

<--------------------- Undoing Mistakes: restore / stash --------------------------->
<-------------------------------------------------------------------------------->

# CASE 1 - Wrote wrong code, NOT committed yet:
git restore .                              # undo ALL uncommitted changes, back to last commit
git restore model.py                       # undo just this one file
git restore model.py train.py              # undo just these two files
git restore --staged fileName              # unstage a file (keep the edit, remove from "add")
git clean -n                               # DRY RUN: preview which untracked files would be deleted
git clean -f                               # actually delete untracked files
git clean -fd                              # also delete untracked directories
# USE CASE: you wrote bad code, haven't committed it, and want to go back to the
# last saved version.
# ALTERNATIVE (older, still works, not recommended anymore): git checkout -- <file>
# used to do the same thing as "git restore <file>" before "restore" was added.

# CASE 2 - Need to switch branches but have messy uncommitted work:
git stash                                  # save uncommitted changes, revert files to clean state
git stash push -m "wip attention crop fix" # same, but with a label
git stash list                             # see all stashed items
git stash pop                              # re-apply the LAST stash AND remove it from the list
git stash apply                            # re-apply the LAST stash but KEEP it in the list
git stash apply stash@{1}                  # re-apply a SPECIFIC (not last) stash
git stash drop stash@{1}                   # delete a specific stash without applying it
git stash clear                            # delete ALL stashes (careful, cannot be undone)
# USE CASE: any time you need to "set aside" unfinished work without committing it.
# ALTERNATIVE: git stash -u  -> also includes untracked (new) files in the stash
# (plain "stash" ignores new untracked files by default).


<-------------------------------------------------------------------------------->
<--------------------------- git revert (detailed) ------------------------------->
<-------------------------------------------------------------------------------->

# revert = undo a COMMITTED change by creating a NEW commit that reverses it.
# The old commit is NOT deleted. History stays intact. Safe for shared branches.

# CASE 1 - Last commit is the wrong one:
#   History:  A---B---C   (C is bad)
git revert C
#   Result:   A---B---C---D     (D = undoes C)

# CASE 2 - An OLD commit (not the latest) is the wrong one:
#   History:  A---B---C---D---E   (B is bad)
git revert B
#   Result:   A---B---C---D---E---F     (F = undoes B, HEAD stays at E)
#   Git does NOT rewind you to B; it stays at the latest point and applies
#   the OPPOSITE of B's changes on top of the current code.

# CASE 3 - Later commits depend on the one you're reverting -> CONFLICT risk:
#   A = add function(), B = code starts using function(), C = builds on that
#   git revert A -> may raise CONFLICT because B and C rely on A.
#   Even without a conflict, program LOGIC might still break - Git only
#   understands TEXT changes, not whether your model/code still makes sense.
git status
git diff
#   then re-run your tests / training / validation.

# CASE 4 - Commit touched multiple files:
#   revert reverts ALL files from that commit, not just one - this is why
#   commits should be one logical change, not "update everything".

# CASE 5 - Revert with a conflict:
git revert <hash>
git status                                 # shows which files conflict
#   ... manually fix the conflicting lines ...
git add <file>
git revert --continue                      # finish the revert after fixing
git revert --abort                         # or cancel the revert entirely

# CASE 6 - Revert a whole range of commits:
git revert --no-commit A..D                # reverts A,B,C,D without auto-committing each
git commit -m "revert: remove failed focal-loss experiment"
# USE CASE: undo the effect of a commit that's ALREADY been shared (on main or a
# shared branch) without deleting its history — very safe for shared branches.
# ALTERNATIVE if the commit is still local and nobody has seen it: use "git reset"
# instead of "revert" (see the reset section below) — simpler since it doesn't
# leave a trace that you made a mistake in history.


<-------------------------------------------------------------------------------->
<------------------------ git commit --amend ------------------------------------->
<-------------------------------------------------------------------------------->

# CASE 1 - Forgot a file in the last commit (e.g. a config file or Slurm script):
git add forgotten_file.py
git commit --amend --no-edit               # adds file into LAST commit, same message

# CASE 2 - Typo in the last commit message:
git commit --amend -m "feat: add attention module (fixed typo)"

# WARNING: only amend commits that have NOT been pushed yet. Amending a commit
# already on GitHub rewrites history, same problems as reset --hard + force push.
# USE CASE: you forgot a file or made a typo in the message of the LAST commit,
# and haven't pushed it yet.
# ALTERNATIVE if the mistake is older than the last commit: git rebase -i HEAD~n
# and choose "edit" on the commit you need to fix.

<--------------------------- git cherry-pick ------------------------------------->
<-------------------------------------------------------------------------------->

# CASE: You made a good fix on experiment/focal-loss (a throwaway branch),
# and want THAT ONE commit on feature/attention-model, without merging
# the whole experiment branch.
git log --oneline experiment/focal-loss    # find the commit hash, e.g. 9f3d21
git switch feature/attention-model
git cherry-pick 9f3d21                     # copies just that one commit onto this branch
# USE CASE: you made a good fix on a throwaway/experiment branch and want just that
# ONE commit on another branch, without merging the whole branch.
# ALTERNATIVE for several commits at once: git cherry-pick <hash1>..<hash2> (a range),
# or git cherry-pick -n <hash> if you want to stage the change without an
# automatic commit (so you can edit it first).


<-------------------------------------------------------------------------------->
<------------------- git reset: unstaging vs rewriting history -------------------->
<-------------------------------------------------------------------------------->

# git reset has 3 modes, from gentlest to most destructive:

git reset fileName                         # UNSTAGE a file (undo "git add"), keeps the
                                            # code changes visible on screen/working dir
                                            # -> use this to undo an accidental "git add"

git reset --soft <hash>                    # move branch pointer back, but keep ALL changes
                                            # from the undone commits STAGED (ready to re-commit)

git reset --mixed <hash>                   # (default if you don't specify) moves branch back,
                                            # changes go to working dir, UNSTAGED

git reset --hard <hash>                    # moves branch back AND discards the changes
                                            # completely (see full danger case below)
# USE CASE:
#   reset fileName (no flag): just want to remove a file from staging.
#   --soft: want to go back commits but keep the changes ready to re-commit differently.
#   --hard: you're 100% sure you want to fully delete those changes, and the branch
#   is usually LOCAL and nobody else has seen it.

# CASE - full example of reset --hard:
#   History:  A---B---C---D   (you are on D)
git reset --hard B
#   Result:   A---B          (branch pointer + working files both revert to B.
#                              C and D are no longer part of the branch's state.)

# Why dangerous:
#   - C and D never pushed -> mostly safe, recoverable via reflog.
#   - C and D ALREADY pushed to GitHub, then you force push:
git push --force
#     -> rewrites the remote branch's history. Anyone who pulled C/D now has
#        a mismatched history. This is the real danger.
# ALTERNATIVE (safer than --hard on a pushed branch): use "git revert" instead of
# "reset --hard" + "push --force" — this way you don't break your teammates' history.

# Rule of thumb:
#   Branch is private/local only        -> reset --hard is fine to use
#   Branch is shared or already pushed  -> use revert instead
#   Just want to undo a "git add"       -> plain git reset (no flags/hash)
#   Want to keep the code but re-commit differently -> reset --soft


<-------------------------------------------------------------------------------->
<----------------------------- git reflog ---------------------------------------->
<-------------------------------------------------------------------------------->

# Use when you made a scary mistake (like reset --hard) and think you lost work.
git reflog
# Example output:
#   a81c91  HEAD@{0}: reset: moving to B
#   9f3d21  HEAD@{1}: commit: feat: add attention   <- this is your "lost" work
#   4c77a3  HEAD@{2}: commit: feat: add baseline

git reset --hard 9f3d21                    # get back to the lost commit
# or: git switch -c recovered-branch 9f3d21

# reflog = your safety net, LOCAL only (not on GitHub, not shared with others).
# Git rarely actually deletes anything immediately.
# USE CASE: you made a scary mistake (like a wrong "reset --hard") and think you
# lost work — this is your local safety net.
# NOTE: reflog is LOCAL ONLY (not on GitHub, not shared with anyone) and there's no
# real alternative with the same job.


<-------------------------------------------------------------------------------->
<------------------- Clarifying the confusing commands: reset vs stash vs restore vs revert ->
<-------------------------------------------------------------------------------->

# git reset (plain, no --hard)  -> UNSTAGING: removes files from staging area,
#                                   keeps the code changes visible. Undoes "git add".
# git stash                     -> HIDING: takes ALL uncommitted changes and stores
#                                   them away, returns files to a clean state.
#                                   Use when you need to switch branches urgently
#                                   mid-work. Bring back later with "git stash pop".
# git restore <file>            -> UNDOING (uncommitted): throws away local edits
#                                   to a file, back to its last committed version.
# git revert <hash>             -> UNDOING (committed): creates a NEW commit that
#                                   cancels out an OLD commit. History preserved.
# git reset --hard <hash>       -> REWRITING history: moves the branch pointer
#                                   backward and discards commits. Use carefully.
#
# EASY RULE OF THUMB:
#   Still in your hands, not committed yet -> "restore" (one file) or "stash" (everything).
#   Already committed -> "revert" (if branch is shared) or "reset" (if branch is local/private).

<--------------------------- Tags & Releases -------------------------------------->
<-------------------------------------------------------------------------------->

git tag                                    # list all tags
git tag v1.0.0                             # lightweight tag on current commit
git tag -a v1.0.0 -m "Baseline5 - Val F1 0.75"   # annotated tag WITH a message (preferred)
git tag -a v1.0.0 -m "message" <hash>      # tag a SPECIFIC older commit, not just current

git show v1.0.0                            # see the commit + message the tag points to

git push origin v1.0.0                     # push ONE tag to GitHub
git push origin --tags                     # push ALL local tags to GitHub

git tag -d v1.0.0                          # delete a local tag
git push origin --delete v1.0.0            # delete that tag from GitHub too
# USE CASE: you have a good experiment result (e.g. best Val F1) and want to
# permanently "bookmark" that commit so you can easily come back to it later.
# ALTERNATIVE (simpler, no formal tag needed): manually log the commit hash in an
# experiment log file (see the "CASE - Tracking ML experiments" example below) —
# faster but less precise and easy to forget.

# ---------------- Concept: Tag vs Release ----------------
# Tag     -> a core Git feature: a permanent bookmark pointing to one commit.
# Release -> a GitHub feature: wraps around a Tag with a title, description,
#            and auto-generated downloadable zip/tar.gz files of the code.

# How to create a Release:
# Step 1 (Terminal):
git tag v1.0
git push origin v1.0
# Step 2 (GitHub website):
#   1. Go to your repo -> click "Releases"
#   2. Click "Draft a new release"
#   3. Choose the tag you pushed (v1.0)
#   4. Write a title + release notes
#   5. Click "Publish release"

# Can I make a Release WITHOUT tagging first in the terminal?
#   Yes - if you forget, you can type a new tag name directly on the GitHub
#   Release page and GitHub creates the Tag for you automatically.
#   But every Release MUST be attached to a Tag either way.

# Where do the zip files come from?
#   GitHub auto-generates "Source code (zip)" / "(tar.gz)" based on the exact
#   code that existed at the moment the Tag was created.

# CASE - Tracking ML experiments through tags/commits (relevant to your project):
# In your experiment log / README, write:
#   Experiment: EXP-014
#   Commit: 8d4a12f   (or tag: v1.2.0)
#   Model: ResNet50 + LSTM + Attention
#   Loss: Focal Loss, LR: 1e-4, Batch: 16
#   Best Val F1: 0.753
# Later, to get back to EXACTLY that code:
git switch --detach 8d4a12f                # or: git switch --detach v1.2.0

<--------------------------- Ignoring Files & Large ML files --------------------->
<-------------------------------------------------------------------------------->

touch .gitignore                           # create the ignore file

# Typical content for an ML project like yours:
#   __pycache__/
#   *.pyc
#   *.log
#   *.pth
#   *.pkl
#   runs/
#   outputs/
#   checkpoints/
#   videos/
#   datasets/
#   .ipynb_checkpoints/
#   .env

*.log                                      # Git will not track any file ending with .log
!vip.log                                   # "!" force-includes a file even if a broader
                                            # pattern above would normally ignore it

git add -f text.txt                        # force-add ONE file even if .gitignore blocks it

git rm -r --cached checkpoints/            # if a folder was ALREADY tracked by mistake,
                                            # untracks it (keeps files on disk, stops Git
                                            # from tracking it going forward) - then commit
# USE CASE: keep files like checkpoints/logs/datasets out of Git so the repo stays
# small and fast.
# ALTERNATIVE (instead of writing .gitignore by hand): gitignore.io gives you a
# ready-made .gitignore file based on your language/framework (Python, PyTorch, etc).

# CASE - you genuinely need to version large files (checkpoints, datasets):
# Regular Git is NOT built for this. Use Git LFS (Large File Storage):
git lfs install                            # one-time setup per machine
git lfs track "*.pth"                      # tell Git LFS to handle all .pth checkpoint files
git add .gitattributes                     # records the LFS tracking rules
git add checkpoint_best.pth
git commit -m "chore: add best checkpoint via LFS"
git push
# Without LFS, committing multi-GB checkpoints directly bloats the repo and
# makes clone/pull painfully slow for everyone (including future you).
# USE CASE: you actually need to version large files (checkpoints, datasets) INSIDE
# Git history, not just ignore them.
# ALTERNATIVE for storing large ML files (often better than Git LFS for ML projects):
#   DVC (Data Version Control) -> built specifically for ML/data projects, same idea
#   as Git but for data and models, integrates with S3/GCS/etc.
#   Or: upload files to external storage (S3, Google Drive, Kaggle itself) and just
#   store the link/version in the repo instead of the file itself.

<------------------- Pull Requests, Forking & Team Workflow Concepts ------------->
<-------------------------------------------------------------------------------->

# --------------- CASE 1: Working with a team on the same repo ---------------
# When: you're in a company or group project, everyone shares the same repository.
# What happens: instead of editing main directly, you create a branch, push it,
# and open a Pull Request. It tells your team: "please review my code before merge."

# --------------- CASE 2: Contributing to someone else's project (Open Source) ---
# When: you find a GitHub project, want to fix a bug, but have no edit permission.
# What happens: you Fork it (take your own copy), make changes, push to YOUR
# fork, then open a Pull Request to the original owner: "I fixed this in my
# version, please pull it into your project."

# --------------- The full PR workflow ---------------
# 1. Push:  upload your finished branch to GitHub   (git push origin featureX)
# 2. PR:    open GitHub, click "Compare & Pull Request"
# 3. Merge: click "Merge" on GitHub to add the code to the online main branch
# 4. Local is now outdated (your laptop's main branch didn't get the update)
# 5. Pull:  git checkout main -> git pull origin main

# --------------- Standard daily steps ---------------
# 1. Update local main:   git checkout main -> git pull origin main
# 2. Create a branch:     git checkout -b <branch_name>
# 3. Save work locally:   git add . -> git commit -m "message"
# 4. Push to GitHub:      git push origin <branch_name>
# 5. Open Pull Request on GitHub
# 6. Merge PR on GitHub
# 7. Sync laptop:         git checkout main -> git pull origin main
# 8. Clean up:            git branch -d <branch_name>
# ALTERNATIVE: if you use a different platform than GitHub — GitLab calls this
# same idea "Merge Requests" (same concept, different name), Bitbucket also calls
# it Pull Requests.


<-------------------------------------------------------------------------------->
<--------------------------- Quick Decision Table --------------------------------->
<-------------------------------------------------------------------------------->

# Edited a file, NOT committed yet, want to undo it?          -> git restore <file>
# Want to undo an accidental "git add"?                        -> git reset <file>
# Need to switch branches but have messy uncommitted work?     -> git stash
# Already committed, want to undo its effect (history kept)?   -> git revert <hash>
# Want to move your PRIVATE branch back in time?                -> git reset --hard <hash>
# Want to undo a commit but keep the code changes staged?       -> git reset --soft <hash>
# Forgot a file / typo in the LAST commit (not pushed yet)?     -> git commit --amend
# Want one specific commit from another (throwaway) branch?     -> git cherry-pick <hash>
# Did a reset/rebase mistake and lost your place?               -> git reflog
# Starting a new independent task?                               -> git switch -c <type>/<name>
# Small fix inside the task you're already on?                  -> commit on same branch
# Finished the branch, want it merged?                           -> push + Pull Request on GitHub
# Want to mark a result-worthy version of the code?              -> git tag -a (+ GitHub Release)
# Accidentally tracked checkpoints/logs/datasets?                -> .gitignore + git rm --cached
# Checkpoints/datasets are too big for normal git?                -> Git LFS
# Forgot to delete the remote branch after merging?               -> git push origin --delete <name>
#   (note: git pull will NOT bring a deleted branch back)

<--------------------------- Daily Golden Routine --------------------------------->
<-------------------------------------------------------------------------------->

git status                                 # BEFORE anything
git diff                                   # BEFORE commit
git log --oneline --graph --all            # AFTER commit, to see history

git switch main                            # BEFORE new feature
git pull
git switch -c feature/<name>

# while working:  edit -> status -> diff -> add -> commit -> push  (repeat)

# after finishing: push -> Pull Request (GitHub) -> review -> merge (GitHub)
#                  -> git switch main -> git pull -> git branch -d feature/<name>

# after a good experiment result: git tag -a vX.Y.Z -m "description + metric"
#                                  (optionally publish as a GitHub Release too)

<--------------------------- Golden Rules (summary) ------------------------------->
<-------------------------------------------------------------------------------->

main        = stable version, always working. Never code directly on it.
branch      = one independent task
commit      = one logical checkpoint
push        = upload local commits to GitHub  (does NOT mean branch is done)
fetch       = download remote info, don't touch my branch
pull        = fetch + merge into MY current branch (not necessarily "main"!)
merge       = happens on GitHub via Pull Request (recommended) or locally
stash       = temporarily shelve uncommitted work without committing
restore     = undo an UNCOMMITTED local change
reset       = (no flag) unstage a file | --soft keep changes staged |
              --mixed keep changes unstaged | --hard discard changes entirely
amend       = fix the LAST commit (message or forgotten file) before pushing
cherry-pick = copy ONE specific commit from another branch
revert      = undo a COMMITTED change safely (history kept, new commit made)
reflog      = recovers your position after a history mistake (local only)
tag         = permanent label on a commit; Release = GitHub wrapper around a tag
.gitignore  = keeps junk/generated files (logs, checkpoints, __pycache__) out of git
Git LFS     = the correct way to version large binary files (checkpoints, datasets)

<--------------------------- Quick Alternatives Summary --------------------------->
<-------------------------------------------------------------------------------->

# Original command              -> Well-known alternative
# git checkout -b                -> git switch -c
# git checkout <file>            -> git restore <file>
# git checkout <hash>            -> git switch --detach <hash>
# git merge                      -> git rebase (if you want linear history)
# git rebase -i (clean commits)  -> GitHub "Squash and merge"
# git push --force                -> git push --force-with-lease (safer)
# git pull                        -> git pull --rebase
# Git LFS                         -> DVC (Data Version Control)
# RSA SSH key                     -> ED25519 SSH key (newer, faster)
# writing .gitignore by hand      -> gitignore.io
# Git Flow (full branch system)   -> manual branch naming like in this sheet
